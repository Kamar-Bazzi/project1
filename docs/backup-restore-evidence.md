## What was compared

- application table set;
- normalized column definitions;
- primary, unique, foreign-key, and check constraints;
- indexes, PostgreSQL enum values, extensions, views, triggers, functions, and
  row-level policies;
- per-table row counts;
- order-independent SHA-256 content fingerprints using canonical JSONB rows;
- sequence names and last-value/called state;
- Prisma migration history;
- all five enabled clinical relation-integrity triggers introduced by the
  latest migration; and
- deterministic fixture markers, including Unicode text handling.

The source is fingerprinted both before and after `pg_dump`. A difference fails
the run rather than comparing a moving source to a restore. The target must
contain zero application tables before `pg_restore`; therefore a successful
comparison cannot be the result of restoring over a pre-populated database.

## Safeguards and limitations

The automatic cleanup code will drop only database names beginning with
`caretrack_source_verify_` or `caretrack_restore_verify_`. This run confirmed
both cleanup flags. A prematurely killed operating-system process may bypass a
language-level `finally` handler; operators should therefore list databases
with those prefixes after an interrupted run and remove only a verified drill
database.

This is strong logical-backup evidence, but it is not a complete disaster
recovery certification:

- source and target were on the same local PostgreSQL server and storage host;
- the small deterministic fixture does not measure production-scale recovery
  time or storage capacity;
- no encrypted off-site object-store download, cross-host network path, key
  recovery, or PostgreSQL major-version upgrade was exercised;
- Docker image execution was not used because the local Docker Desktop Linux
  daemon was unavailable; native PostgreSQL client tools were used instead;
- no active writers were present, so the source-stability guard passed under a
  deliberately quiescent workload; and
- RPO/RTO, retention compliance, operator access, and off-site replication must
  be measured in the actual hosting environment.

Before production approval, repeat the restore from the off-site encrypted
copy onto a separate host, run API smoke tests against it, measure recovery
time, verify monitoring/alerts, and securely destroy the drill environment.
